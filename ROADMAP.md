# PANDA_Package — анализ задачи и roadmap

Источник: `PANDA_Package.pdf` (МФТИ, 2026, 16 стр.). Целевой журнал — Computer Physics Communications.

## 1. Суть задачи

PANDA — рабочий научный код для анализа межфазных границ и капиллярных состояний
жидкости в порах: траектория МД (GROMACS `.xtc`/`.gro`) → профиль плотности → фит
аналитической моделью формы интерфейса.

Код рос под конкретные расчёты, физика и инфраструктура смешаны. Задача — не «причесать
Python», а **спроектировать расширяемую архитектуру**, где новая пора или новая форма
добавляется без правки ядра. Путь: **научный код → библиотека → PyPI → статья**.

Предметная модель — два уровня, которые нельзя смешивать:

```
Пора (геометрия) ──► допустимые формы интерфейса ──► своя аналитика у каждой формы
TrianglePore         Droplet / Thread / Capsule        ρ(r), площадь, границы существования
```

Конвейер данных:

```
траектория → центрирование → профиль плотности → фит → результат
```

## 2. Ключевые технические задачи

| #   | Задача                              | Суть                                                                  | Критерий                                                   |
| --- | ----------------------------------- | --------------------------------------------------------------------- | ---------------------------------------------------------- |
| A   | Абстракция формы (`InterfaceShape`) | профиль, площадь, границы существования, ограничения, геометрия       | у каждой формы своя математика, а не просто другие параметры |
| B   | Абстракция поры                     | геометрия + `available_shapes`                                        | пора знает формы, форма знает аналитику                    |
| C   | Параметры (`Parameter`)             | value + bounds, модель сама описывает свои параметры                  | единое описание для всех форм                              |
| D   | Общий оптимизатор                   | вектор только из свободных параметров; `optimize=[...]`, `fixed={...}` | φ, (δ,φ), (θ,δ,φ) — без веток в коде                       |
| E   | Центрирование как отдельный этап    | стратегии `liquid` / `pore`; форма/пора задаёт предпочтительную       | не спрятано внутри аналитики                               |
| F   | Объект результата                   | параметры, ошибки, качество фита                                      | общий для всех моделей; задел для сравнения моделей        |
| G   | CLI                                 | `panda profile …`, `panda fit … --shape auto`                         | единая понятная логика, а не максимум команд               |
| H   | Документация тестов + тесты         | сценарии в `tests/README.md` → pytest                                 | проверяется физическая правильность, а не «не падает»      |
| I   | Синтетическая валидация             | synthetic shape → ρ + шум → centering → fit → сравнение с истиной     | Δθ(σ_ρ), зависимость от дискретизации, сравнение центрирований |
| J   | Упаковка и релиз                    | src-layout, `pyproject.toml`, LICENSE, CITATION.cff, CI, docs         | `pip install` работает; TestPyPI → PyPI                    |

Явные ограничения из документа:

- на первом этапе ничего серьёзно не переписывать — только разбираться;
- сначала спроектировать и обсудить API, только потом переносить математику;
- прототип — минимум для **двух типов пор**;
- тесты появляются вместе с прототипом, а не после.

**Проблемы, уже найденные в ноутбуке `R/theta_contact_panda.ipynb`** (требования к новому коду):

- `profile_approx_from_array` всегда поднимает `ProcessPoolExecutor`, даже при `n_jobs=1`, — ненадёжно под Windows/Jupyter.
- Вне области существования (φ_min, φ_max) модель возвращает NaN → L-BFGS-B может упасть в Fortran-коде;
  нужна явная обработка границ существования в оптимизаторе.
- На реальном профиле BENZ (двугорбый, насыщающийся) roll-фит визуально плохой → нужны метрики
  качества фита и сравнение форм, а не только θ.
- ρ_bulk, φ, центрирование считаются ad hoc в каждом ноутбуке заново → кандидаты в `core/`.

**Треугольных/цилиндрических пор (из PDF) нет** ни в библиотеке, ни в `Dev_PANDA`, ни в ноутбуках:
реализована только плоская щель (формы droplet, doughnut, worm, roll, perforation, layer).
Для «второй поры» в прототипе нужны формулы → источник уточнить (возможно, `roughness_2/25_MS_RectCellInterfaceShape.pdf`).

### Фаза 1. Аудит текущего кода (1–2 нед.) → схема кода, схема моделей

**Статус (28.09.2026): отчёт по 10 пунктам первой задачи PDF — [`docs/task1_current_panda.md`](docs/task1_current_panda.md);
рабочие заметки — [`docs/phase1_audit.md`](docs/phase1_audit.md).** Главное:
4 модуля `alpha/theta/delta/pi` численно ≡ одна модель с разными фиксированными параметрами;
`center_by` в коде не существует; S(θ,δ) не реализована; статья про прямоугольную ячейку даёт
параметр k щели, а не вторую пору. Осталось: golden master на реальных профилях (`npys/`).

Первые наблюдения при установке (проверить в аудите):

- Формы: droplet, doughnut, worm, roll, perforation, layer (+ AntiDroplet/AntiRoll в `geom/interface_geom`).
  Режимы фита — `extention="alpha"` (θ,δ) / `"theta"` / `"delta"`; выбор функции через
  `getattr(interface, f"rho_{type}_{extention}")` и ветки `if extention == ...` в `minimize_worker`.
- В `interface/alpha.py` функции `grad_rho_worm_theta` и `grad_rho_perforation_theta` названы с суффиксом
  `_theta` — похоже на опечатку (градиент для alpha-режима тогда не находится).
- Мусорные файлы в пакете: `panda/#angle_blocks.py#`, `panda/geom/Roll copy.py`.
- `scipy.minimize(..., options={"disp": ...})` даёт `OptimizeWarning: Unknown solver options: disp`
  на scipy 1.18.1.
- Дефолт `x0=(3π/4, 0.1)`; θ хранится в радианах.

1. Карта модулей и зависимостей.
2. Таблица «пора × форма → где ρ(r), площадь, границы существования, какие параметры».
3. Где выбирается режим φ / (δ,φ) / (θ,δ,φ), где центрирование, где дублирование кода.
4. Разделение функций на универсальные и специфичные для формы.
5. **Эталонные выходы (golden master)** текущей версии на рабочем примере — страховка от
   регрессий при переносе математики.

## 4. Риски

- **Регрессии при переносе математики** → golden master из Фазы 1.
- **Интерфейс формы не подойдёт к реальной математике новых пор** → квадратная пора уже в прототипе ядра; треугольная проверяет несимметричный профиль и формы без профиля.
- **Модели многоугольных пор ещё меняются** → эталон привязан к коммиту PANDA_Polygon, перенос формул — отдельная фаза 4а.
- **Формулы смачивающего режима отсутствуют** (старые при θ < 90° неверны: ∫ρ ≠ φ) → получить или вывести; до этого формы объявляют только несмачивание.
- **Плохая обусловленность фита (θ,δ,φ)** — корреляция θ и δ, локальные минимумы → мультистарт, масштабирование.
- **Разрастание объёма** → CLI, графики, автовыбор модели вторичны; ядро важнее.
